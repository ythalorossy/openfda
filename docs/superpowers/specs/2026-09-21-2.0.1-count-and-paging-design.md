# 2.0.1 Design: Count Correctness and Sound Paging

**Date:** 2026-09-21
**Release:** 2.0.1
**Scope:** six correctness defects reported against 2.0.0

## Overview

Six defects reported against 2.0.0 reach a caller as a wrong answer. All six
are fixed here. Two further reported items are quality problems that change
returned record shapes; they are deferred to 2.1.0 and listed under
[Out of Scope](#out-of-scope-deferred-to-210).

| # | Defect | Section |
| --- | --- | --- |
| 2 | 14 of 30 declared `count` fields are rejected upstream | [1](#section-1--the-count-field-chain-defects-2-4-7) |
| 4 | A rejected `count` surfaces as an outage, not a bad argument | [1](#section-1--the-count-field-chain-defects-2-4-7) |
| 7 | `drugsfda` `count=sponsor_name.exact` reports an empty dataset | [1](#section-1--the-count-field-chain-defects-2-4-7) |
| 3 | `limit` caps `count` buckets at the *record* default | [2](#section-2--limit-means-buckets-under-count-defect-3) |
| 1 | Nothing tells a caller that `skip += limit` is unsound | [3](#section-3--sound-paging-defect-1) |
| 6 | `drug-shortages` documents `status` values the dataset lacks | [4](#section-4--shortages-status-vocabulary-defect-6) |

Every claim below was verified against the live API on 2026-09-21. Where the
report's diagnosis differed from what the code actually does, the verified
behaviour is what this spec designs against; those divergences are recorded in
[Corrections to the Report](#corrections-to-the-report).

## Section 1 — The count-field chain (defects 2, 4, 7)

### The single underlying cause

Defects 2, 4 and 7 are one defect seen from three angles: **nothing in the
repository knows which paths openFDA can actually aggregate.**

The existing guards each prove a different property, and none proves this one:

- `tests/catalog-conformance.test.ts` proves a path is **published** (offline,
  against the committed FDA field reference).
- `scripts/probe-fields.ts` proves a path is **populated** (live,
  `_exists_:<path>`).
- Nothing proves a path is **countable**.

Countability is a separate property of openFDA's index mapping, and it has no
derivable rule.

**14 of the 30 declared `countFields` fail.** Verified live 2026-09-21, with
the working form in each case:

| Endpoint | Declared (fails) | Corrected to | Upstream response |
| --- | --- | --- | --- |
| `enforcement` | `classification` | `classification.exact` | 500 `illegal_argument_exception` |
| `enforcement` | `status` | `status.exact` | 500 `illegal_argument_exception` |
| `enforcement` | `state` | `state.exact` | 500 `illegal_argument_exception` |
| `enforcement` | `voluntary_mandated` | `voluntary_mandated.exact` | 500 `illegal_argument_exception` |
| `ndc` | `dosage_form` | `dosage_form.exact` | 500 `illegal_argument_exception` |
| `ndc` | `route` | `route.exact` | 500 `illegal_argument_exception` |
| `ndc` | `product_type` | `product_type.exact` | 500 `illegal_argument_exception` |
| `label` | `openfda.route` | `openfda.route.exact` | 500 `illegal_argument_exception` |
| `label` | `openfda.product_type` | `openfda.product_type.exact` | 500 `illegal_argument_exception` |
| `orangebook` | `products.dosage_form` | `products.dosage_form.exact` | 500 `illegal_argument_exception` |
| `orangebook` | `products.route` | `products.route.exact` | 500 `illegal_argument_exception` |
| `drugsfda` | `products.dosage_form` | `products.dosage_form.exact` | 500 `illegal_argument_exception` |
| `drugsfda` | `sponsor_name.exact` | **`sponsor_name`** | 404 `"Nothing to count"` |
| `shortages` | `dosage_form` | `dosage_form.exact` | 500 `illegal_argument_exception` |

The report tallies 13 because it breaks the `drugsfda` `sponsor_name.exact`
row out separately as defect 7. It is the same correction, so this spec counts
it here and treats defect 7 as the classification bug that row exposes.

**Why the suffix is not a rule.** 16 declared fields pass as declared, and
they are not distinguishable by shape from the ones that fail:
`ndc.marketing_category`, `drugsfda.products.marketing_status`,
`shortages.status`, `shortages.therapeutic_category`,
`orangebook.products.application_type` and
`orangebook.products.therapeutic_equivalence_codes` all aggregate **bare**,
while near-identical low-cardinality strings on the same endpoints require
`.exact`. And `drugsfda.sponsor_name` runs the other way entirely — `.exact`
is the failing form. All six of `drug-event`'s declared fields pass as
declared. The property must be measured per field and pinned.

### The offline guard: a new `.countable.json` catalog

A new committed artifact, mirroring the existing `.coverage.json` exactly:

```
scripts/fields-countable.mjs        →  npm run fields:countable
src/catalog/drug-<endpoint>.countable.json
```

**Probe method.** One **search-free** `count=<path>` request per candidate.
Search-free is deliberate: it measures the index mapping alone, so the result
is deterministic and independent of any search value. A path is countable if
the request returns 2xx.

**Candidate set.** Each declared `countField` **plus its suffix alternate**
(`status` also probes `status.exact`; `recalling_firm.exact` also probes
`recalling_firm`). Recording both directions is what lets a failing test name
the working alternative instead of only reporting a failure. Roughly 60
requests, completing in seconds.

**File shape:**

```json
{
  "endpoint": "enforcement",
  "probed_at": "2026-09-21T00:00:00.000Z",
  "countable": {
    "classification": false,
    "classification.exact": true,
    "status": false,
    "status.exact": true,
    "recalling_firm": false,
    "recalling_firm.exact": true
  }
}
```

**The guard.** `tests/catalog-conformance.test.ts` gains one offline
assertion: every `countField` on every descriptor appears in the committed
file with `countable: true`.

The load-bearing property is that **absence is a failure, not a pass.** An
author who adds a `countField` without running the probe gets a red test
naming the missing probe entry. A guard that silently passed on unprobed
fields would be the same defect this spec exists to close.

**Bundle.** The file is read from disk through a repo-relative path string,
the way `descriptor.catalog` already is — never `import`ed. It therefore stays
out of `dist/index.js` and off the `tests/bundle-size.test.ts` budget. This
differs from `.coverage.json`, which *is* imported because
`DRUG_CATALOGS` serves it in the MCP resource payload. Countability is not
served in 2.0.1: the probe covers only declared fields, so every entry in the
served long tail would be `null`, paying bundle bytes for no information.

**Weekly re-probe.** `.github/workflows/fields-drift.yml` runs
`fields:countable` alongside the existing steps, so an upstream index
remapping opens an issue rather than surfacing as a broken tool.

### The runtime backstop: a fourth `PageOutcome`

openFDA reports a bad `count` argument in two different ways, and
`src/core/http.ts` mishandles both.

**Verified upstream responses:**

| Request | Status | Body |
| --- | --- | --- |
| `count=status` (text field) | 500 | `SERVER_ERROR` / details: `[illegal_argument_exception] Text fields are not optimised for operations that require per-document field data like aggregations and sorting … Please use a keyword field instead.` |
| `count=sponsor_name.exact` (no such path) | 404 | `NOT_FOUND` / `"Nothing to count"` |
| `count=<valid>` + zero-match search | 404 | `NOT_FOUND` / `"No matches found!"` |
| zero-match search, no `count` | 404 | `NOT_FOUND` / `"No matches found!"` |

The discriminator is clean and sits on the message string: `"Nothing to count"`
always means the count path does not exist or cannot be aggregated;
`"No matches found!"` always means the search matched nothing, with or without
`count`.

Today `src/ApiHandler.ts:88` overwrites the 500's message with
`Server Error: OpenFDA service is experiencing issues` and discards
`error.details`, so the actionable upstream text never reaches the caller
(defect 4). And `src/core/http.ts:38`'s `isNoMatches` classifies *any*
`NOT_FOUND` as a miss, so the 404 case becomes "No drug-drugsfda records
found" — a phantom empty dataset (defect 7).

**`PageOutcome` gains a fourth kind:**

```ts
export type PageOutcome<T> =
  | { kind: 'hit'; data: T }
  | { kind: 'miss' }
  | { kind: 'bad_request'; detail: string }   // NEW
  | { kind: 'error'; error: OpenFDAError };
```

`fetchPage` returns `bad_request` when the body shows either signature:

1. `error.details` contains `illegal_argument_exception` (any status), or
2. status 404 with `error.code === 'NOT_FOUND'` and message exactly
   `"Nothing to count"`.

This check runs **before** `isNoMatches`, because case 2 *is* a `NOT_FOUND`
404. An unrecognised message falls through to today's classification.

**Executor behaviour.** `bad_request` fails immediately and **does not walk
the remaining tiers** — a bad argument fails identically on every tier, so
walking them only multiplies latency and then reports the wrong outcome. The
error quotes the upstream detail and, when the descriptor's sibling suffix is
known to be countable, names it:

```
Cannot aggregate drug-enforcement by "status": openFDA rejected it —
"Text fields are not optimised for operations that require per-document
field data like aggregations and sorting. Please use a keyword field
instead." Try "status.exact" instead.
```

**Retry.** `isRetryableError` currently retries every 5xx, so a deterministic
bad argument costs 4 requests and ~7s of exponential backoff before failing.
`ApiHandler` stops overwriting `details` on a 500 and treats a 500 carrying
`illegal_argument_exception` as non-retryable.

**Defence ordering.** The offline catalog guard is the primary defence; the
runtime classifier is the backstop. Matching upstream prose is brittle by
nature, which is why it is not the primary defence — but it is what turns an
upstream remapping between weekly probe runs into an actionable message rather
than an outage report.

### Field corrections

The 13 failing `countFields` are corrected to their working form, and
`drugsfda`'s `sponsor_name.exact` to bare `sponsor_name`. Because the probe
writes the committed file from the *current* declarations, the plan sequences
this as: probe (records both directions) → correct the declarations → re-probe
to confirm.

`src/core/codes.ts`'s `decodeTerm` already resolves a `codeMaps` entry through
`path.replace(/\.exact$/, '')`, and `validateDescriptor` compares `codeMaps`
keys against `countFields` through the same `stripExact`. Adding or removing a
suffix therefore does not disturb either. `drug-event` is unaffected: all six
of its `countFields` already pass, including the three coded ones.

## Section 2 — `limit` means buckets under `count` (defect 3)

With `count` set, the executor passes the record `limit` straight through as
openFDA's bucket ceiling. `drug-label`'s default `limit` is 1, so
`count=openfda.manufacturer_name.exact` returns **one bucket** under a
`Top 1 values` header. The correct answer for the reported Advil case is six
manufacturers.

The fix needs `limit` to be distinguishable from absent, which it is not
today: `buildInputSchema` attaches `.default(descriptor.limits.default)`, and
the SDK parses input through the schema, so `input.limit` is always populated
by the time `execute` sees it.

**Change.** Drop `.default()` from `limit` in
`src/core/registry.ts`'s `buildInputSchema`, keeping the documented default in
`.describe()`. `execute` already falls back on `descriptor.limits.default`;
nothing else in `src/` or `tests/` reads the Zod default, so the risk is
contained.

```ts
const limit = input.count !== undefined
  ? (input.limit ?? COUNT_BUCKET_DEFAULT)      // 100
  : (input.limit ?? descriptor.limits.default);
```

`COUNT_BUCKET_DEFAULT = 100` lives in `src/core/executor.ts` beside
`SKIP_MAX`. 100 is openFDA's own default bucket ceiling (verified: a
search-free count with no `limit` returns at most 100 buckets), so the
constant states the upstream default explicitly rather than depending on it
implicitly. It is a generic property of openFDA aggregation, not drug
knowledge, so it belongs in `core/` and not in seven descriptors.

**Description fix.** `limit`'s `.describe()` currently reads
`Max records to return.`, which is false whenever `count` is set. It becomes:
`Max records to return; with count set, caps buckets instead (default 100).`

**Count payload.** The aggregated payload gains `limit`. Aggregations carry no
result total, so `returned === limit` is the only signal available to a caller
that buckets were cut off:

```json
{
  "matched_via": "products.brand_name",
  "counted_by": "products.dosage_form.exact",
  "returned": 100,
  "limit": 100,
  "results": [ ... ]
}
```

**Known asymmetry, documented not fixed.** Zod still caps an *explicit* `limit`
at `descriptor.limits.max` — 25 on `drug-label` — so the implicit bucket
default of 100 exceeds what a caller may explicitly request on that tool. The
default is the good path, and lifting the cap only under `count` would require
a second always-loaded schema parameter. That was rejected against the
`tests/schema-budget.test.ts` ceiling of 20,000 characters, of which the seven
drug tools already consume ~17,972. The `.describe()` text above is where a
caller learns the bucket default.

## Section 3 — Sound paging (defect 1)

When `fitToBudget` drops trailing rows, the envelope is already honest —
`buildEnvelope` counts the sliced rows, so `returned` reflects what was
actually sent. Nothing is lost from the payload. What is missing is any signal
that the obvious paging idiom is wrong: a caller advancing `skip += limit`
steps over exactly the rows the budget dropped.

**`buildEnvelope` gains two keys:**

```ts
export interface Envelope<T> {
  matched_via: string;
  skip?: number;
  total: number | null;
  returned: number;
  limit: number;
  dropped_for_budget: number;      // NEW — always present, 0 normally
  next_skip: number | null;        // NEW
  results: T[];
}
```

`next_skip` is `(skip ?? 0) + returned`, and `null` when either:

- the result set is exhausted — `total` is known and `(skip ?? 0) + returned >= total`; or
- the value would exceed `SKIP_MAX` (25,000).

The second clause matters: handing a caller an offset the same tool would then
reject is the same class of defect as handing them one that skips records.

`dropped_for_budget` is always present rather than conditional. A key that
appears only sometimes is a key a model has to guess about; the constant
presence costs ~25 characters and removes the ambiguity. Today the drop count
exists only in the prose header.

**Header.** When `next_skip` is non-null the header appends
`continue from offset N`, so the prose and the JSON agree:

```
Showing 39 of 138 drug-enforcement records matching product_description
(11 omitted to stay within the response budget) — continue from offset 39
```

**Schema cost.** `ENVELOPE_FIELDS` in `src/core/registry.ts` is named in every
tool's description, so two new keys cost roughly 280 characters across the
seven tools, against the 20,000 budget currently at ~17,972. It fits, and
`tests/schema-budget.test.ts` is updated to the new figure.

## Section 4 — Shortages `status` vocabulary (defect 6)

`src/datasets/drug/shortages.ts:33` documents `status` as
`'Shortage / Resolved / Discontinued'`. All three values are wrong. Verified
live, the dataset holds exactly:

| Value | Records |
| --- | --- |
| `Current` | 1153 |
| `To Be Discontinued` | 443 |
| `Resolved` | 7 |

The field description becomes `'Current, To Be Discontinued or Resolved'`, and
the same correction is applied wherever `README.md` and `CLAUDE.md` restate
the vocabulary.

**No new test.** A unit test cannot know upstream's vocabulary, and pinning
these three strings in an assertion would fail on a legitimate upstream
change without saying anything useful. Instead `fields-countable.mjs` prints
each countable field's top terms, so the weekly `fields-drift.yml` run makes a
vocabulary change visible where it can be acted on.

## Out of scope (deferred to 2.1.0)

**Defect 5 — `drug-enforcement` output size.** At `limit: 50` with
`detail: "summary"` the response reaches ~58–60k characters. The budget is
working correctly; the shape is the problem. Measured: ~27k of field text
across the five free-text fields, plus ~30k of pretty-printed JSON key
overhead from 15 keys × 50 rows at `JSON.stringify(…, null, 2)`. The
`drug-drugsfda` fix does not generalise because that one capped a nested
*array*; this is key overhead and long strings. Candidate fixes — trimming the
`summary` projection, a `capText` sibling to `capArray`, or compact JSON —
all change returned record shapes.

**Defect 8 — cosmetic inconsistencies.** Dates are `MM/DD/YYYY` on
`shortages` but `YYYYMMDD` on `drugsfda`, `enforcement` and `orangebook`
(verified); `openfda: {}` can be an empty object; `term_code` echoes `term`
on free-text fields, which `decodeTerm` documents as intentional but which
reads as noise.

Both alter what callers receive and belong in a release whose notes say so.

## Corrections to the report

Recorded because the fixes differ from what the report proposed.

**Defect 1 is not a counting bug.** The report states that records are
silently lost and that `limit` is not honoured. `buildEnvelope` counts the
sliced rows, so `returned` is accurate and the payload is self-consistent. The
real gap is that no field tells a caller to advance by `returned` rather than
`limit` — hence `next_skip` rather than a change to how rows are counted.

**Defect 4's actionable text exists upstream.** The report states the
`illegal_argument_exception` never reaches the caller. It does reach
`ApiHandler`, in `error.details`; `src/ApiHandler.ts:88` discards it. The fix
is to stop discarding it, not to synthesise a message. The report also does
not mention that a 500 is retried, so each rejected count costs 4 requests and
~7s.

**Defect 5 is not a text-length problem.** Half the payload is JSON key
overhead, so capping long strings alone would not bring `limit: 50` back to 50
rows.

**Defect 7 is more severe than "inverted".** `count=sponsor_name.exact`
returns 404 `NOT_FOUND`, which `isNoMatches` treats as a miss, so the tool
reports *"No drug-drugsfda records found"* for a drug that has records. A
phantom empty dataset is worse than an error, because a caller has no signal
that anything went wrong.

**Field count.** The report says 13 of 28 count fields. The descriptors
declare 30, and 14 fail. The report's per-endpoint breakdown
(`enforcement` 4, `ndc` 3, `label` 2, `orangebook` 2, `drugsfda` 1,
`shortages` 1) is correct and sums to 13; the fourteenth is
`drugsfda`'s `sponsor_name.exact`, which the report lists separately as
defect 7. Since both are fixed by the same one-line correction, this spec
counts all 14 under defect 2 and treats defect 7 as the misclassification
that row exposes.
